# 架构映射与实施

## 1. 从责任边界实施

遵守项目自己的层次和模块清单。若项目采用类似 source adapters → schema/domain → application use cases → feature UI → rendering/app shell 的方向：

- schema/domain 保存纯合同、不变量、规范化与可复用算法，不依赖 UI、文件、网络或具体数据库；
- application 通过公开端口协调用例，不复制领域算法，也不包含具体存储/网络细节；
- data access/adapter 实现端口和版本化持久化，不成为第二个业务 owner；
- feature UI 只调用应用层公开命令/DTO，不直连实现、SQL、文件或网络；
- app shell 只装配和路由，不执行第二套业务。

项目结构不同则映射到其真实边界，不强行套目录模板。任何新增/移动模块同步公开 index、exports、manifest、项目引用、装配、门禁和文档。

## 2. 先改合同，再接消费者

推荐依赖顺序：

1. 固定名词、单位、身份、枚举、版本和不变量；
2. 在唯一领域 owner 实现规则与纯函数；
3. 更新应用 DTO、端口和用例；
4. 更新 repository/adapter、缓存键、Worker 消息和持久化；
5. 更新跨 feature 状态协调；
6. 更新 UI、文案、可访问性和响应式；
7. 删除被替代的旧字段、算法、写入口和重复比较器；
8. 更新测试、配置、用户文档和当前状态。

每一步搜索所有调用者。临时编译桥只能在用户选择兼容方案且有明确删除条件时存在；全面替换时不要保留旧 re-export 或双写作为“保险”。

进入每一步前检查名词、合同、owner、兼容和删除语义是否已确认。若出现多个合理方案且项目规则不能决定，立即通过选择题门取得答案；不要先选一种实现到最后再让用户二选一。

## 3. 修根因与单一事实

- 优先调整错误参数、表达式、数据流或 owner，不在多个页面加特殊 if。
- 共享设置只有一个权威事实、合同和写入用例；产品可以有多个 UI 入口，但都调用同一用例且不保存第二份副本。
- 派生结果按 revision/cache key 计算，不保存成可编辑事实。
- 缓存键包含所有会改变结果的规范化输入和策略/算法版本。
- UI 不重新计算领域规则，Worker 不重新定义评分，导入验证和实时计算使用同一公开 evaluator。
- 正式数据、维护者口径和用户声明分别带来源；未知事实不从名称、截图、校区或示例猜测。

## 4. 算法修改

在写代码前明确；任何无法靠正式资料或现有合同确定的分项都要先以选择题解决：

- 输入、输出、单位、坐标/时间/身份约定；
- 硬不变量、可软化条件和不可软化条件；
- 完整性、去重、容量、冲突和 unknown 的语义；
- 排序是否由单一精确分数决定，完全同分如何稳定处理；
- 中止、超时、部分结果和“无解”的证明边界；
- 最坏时间/空间复杂度与实际要观测的指标。

为可枚举的小实例建立独立 oracle，不从生产算法复制逻辑。先证明新评分、剪枝开关、导入重算和排序一致，再做性能优化。

优化时：

- 保持正式结果指纹或明确升级算法版本；
- 只用可证明的乐观上界/下界剪枝；
- 不物化指数笛卡尔积或不受控全对矩阵；
- 取消、超时和截止时间覆盖准备、搜索、证明、序列化和持久化；
- 报告访问状态、证明次数、峰值内存、首次可行解、完整运行和取消延迟，不只报最快一次；
- 不为示例、ID、截图或一次期望结果硬编码答案。

## 5. UI 与交互

页面应让第一次使用者无需教程完成主流程：

- 设置入口的数量和位置服从已确认的产品设计；每个入口都应指向同一权威事实，并用一致的领域命名；
- 默认值、来源、上限、目标和当前占用分别显示；
- 硬要求与软偏好逐项可辨，不用颜色作为唯一信息；
- 空数据、全过滤、待核、冲突、无解、运行中、暂停、超时和旧结果都有明确状态；
- 用户改变设置时动态重算轻量派生，不启动不必要网络或指数搜索；
- 保存、应用、预览、删除和切换校区等动作边界清晰，不静默改写其它资料；
- 复用字号、卡片和组件规范；合并同类信息但保留可解释明细；
- 支持键盘、读屏、窄屏、短屏、缩放和内部可控横向滚动。

不要仅靠截图判断布局。用 DOM/AX 检查实际高度、溢出、可命中性、disabled/checked/value 和动态文本，再用截图确认视觉层级。

## 6. 增量实现与持续回归

- 从最小反例开始，先让旧实现失败；
- 每完成一个 owner 或合同就跑最近的定向测试和类型检查；
- 数据/存储迁移单独验证成功、失败、重试、旧版本和并发；
- UI 先验证状态和行为，再做视觉微调；
- 性能优化每步保留正确性对照；
- 发现计划遗漏时，判断它是技术必然项还是新产品决定；后者立即暂停依赖分支并以选择题询问，不把它留到测试结果或最终交付。

用户在实施中补充要求时更新决策登记、计划、合同和测试，不把新规则只塞进 UI。用户推翻旧决定时删除过期实现，不同时保留两个活跃口径。

## 7. 工作树纪律

- 修改前后查看 git status，识别用户已有更改；
- 只编辑目标工作副本和本轮文件；不复制整棵树覆盖其它版本；
- 不使用 reset --hard、checkout --、clean 或无目标递归删除；
- 不格式化无关文件，不自动提交生成物或私人数据；
- 临时 server、profile、benchmark 输出和截图写入临时/约定目录，结束时清理或停止；
- 文件删除必须与计划和用户授权一致，并说明可恢复方式。
