# 发现、计划与澄清

## 1. 开始检查

先建立可证明的作用域：

1. 从目标文件向上查找并完整读取适用的 AGENTS.md、RULE.md 或同类规则。
2. 读取规则点名的开始文档、产品范围、工程规则、架构清单、当前状态、计划索引、工作流和发布规则。
3. 运行只读 git status、当前分支/工作树检查，辨认用户已有修改、未跟踪文件和可能的冲突。
4. 确认唯一可写工作副本以及正式版、测试版、镜像、数据仓库或外部计划的只读边界。
5. 确认本轮的权威需求来源。用户若指定“只参考两份桌面计划”，就不把仓库旧计划重新混入。
6. 记录本轮明确不做的事项，以及提交、推送、部署是否获授权。

不要因目录名相近就假设目标仓库。通过真实路径、分支、remote、页面标题、端口或版本标识交叉确认；尤其避免在测试版验收开发版需求或连接到旧的本地服务。

## 2. 现状与责任图

在写方案前回答：

- 当前用户行为和失败/缺口是什么？能否用最小反例或页面流程复现？
- 哪个模块对规则拥有唯一责任？是否已有可复用算法、合同、映射或设置？
- 数据从哪里产生，经过哪些 schema/domain、应用用例、存储/适配器、状态协调和 UI 消费？
- 哪些缓存、备份、导入导出、Worker、命令行、脚本、发布投影或文档也消费该合同？
- 当前测试能证明什么，哪些行为只是看起来存在？
- 正式来源、维护者约定、用户输入和推断是否被清楚区分？

优先搜索符号、公开入口和调用者，不按文件名猜架构。查看 manifest、exports、项目引用和门禁，防止只改主路径而漏掉运行时装配或旧入口。

## 3. 建立需求与决策登记

把每项需求分类为：

- 已确认：用户已选择，后续不得重复询问或擅自改口径。
- 技术必然项：为了让已确认合同在生产者、消费者、测试和文档一致而必须同步；不构成新产品决定。
- 待用户决定：存在多个可观察语义、迁移或长期架构选项，选择会改变结果或数据；登记后立即进入选择题门，不等计划或运行结束。
- 待证据：应先查代码、正式资料或数据，不能让用户替代可完成的技术调查。
- 明确排除：本轮不开发，代码和文档不得暗示已支持。
- 后续候选：有价值但不属于本轮；只记录，不偷偷实现。

“用户没有想到的部分”要先判断性质：

- 若只是同一合同的调用链、验证、备份、文档或删除同步，写入计划并实施。
- 若会增加新按钮、新业务规则、新数据用途、新外部写入或改变旧资料含义，说明理由和影响，立即通过选择题门让用户决定。
- 若修根因必然改变一个已有错误行为，提供最小反例和影响，不把它包装成无关重构。

## 4. 如何询问

只询问会改变产品结果、迁移方式、长期维护或授权边界的问题。先完成足以缩小选项的代码和资料调查；一旦确认仍需用户决定，立即在当前阶段提问，不再继续依赖该决定的计划或实现。

优先使用当前运行环境提供且允许的结构化选择题工具。遵守其题目数量、选项数量和标签约束；通常每批 1–3 题，每题 2–3 个互斥选项，推荐项排第一。相关问题可以小批量提出，但不得跨过当前决策点继续运行，以便“最后统一问”。

每个问题应包含：

- 当前证据和为什么不能仅靠技术判断；
- 两到三个互斥选项；
- 对用户可见行为、数据和维护成本的差异；
- 推荐项及理由，但不替用户选择；
- 一个具体例子，避免抽象术语造成误解。

同类问题成组提出，避免一次只问一个导致反复往返，也避免一次抛出难以回答的长清单。用户没理解时先详细解释原问题，再重新询问；不要把未理解当作同意。

选择题回答后立即写回决策登记并更新计划。没有回答、选择“需要解释”或答案不能映射到任何选项时，仍视为未决；解释后重新用选择题提问。不得用推荐项、默认值或“最兼容方案”代填。

重点检查这些常见决策面：

- 数值语义、单位、边界、默认值、精度和上限是基础值、增量还是最终值；
- 学期/日期/身份采用绝对还是相对表示，哪些展示标签不参与计算；
- 特殊类别计入哪些账、排除哪些容量，是否需要单列；
- 目标、上限、硬约束和软偏好如何相互作用；
- 共用设置的权威事实、唯一写入用例、已确认的编辑入口及消费者；
- 未知、缺失、待核、无解和超支持范围如何显示；
- 旧数据如何迁移，保留桥还是全面替换，失败如何恢复；
- 页面默认、折叠、空状态、响应式和新手流程；
- 性能预算、排序语义、稳定 tie-break 和中止时承诺；
- 保存、备份、隐私、导入导出、日志和网络边界；
- 真实验收、发布、提交和部署权限。

在用户说“暂不执行”期间，不写功能代码、不改运行配置、不启动会产生持久副作用的迁移。默认只做只读调查和用户授权的计划文件编辑。即使原型可逆，静态 mock、交互原型、实验分支或运行状态改动也需要另行授权；未经授权只能在计划中描述建议原型。

## 5. 计划必须可执行

计划至少包含：

1. 状态、目标工作副本、权威来源和“未实施”声明；
2. 目的、范围、明确排除和非目标；
3. 已确认业务规则、来源和适用范围；
4. 当前实现与缺口，列出复用点和要删除的旧路径；
5. 唯一 owner、生产者、消费者、调用者和层间合同；
6. 数据模型、身份、单位、不变量和错误/unknown 状态；
7. UI 信息架构、交互流程、默认值、空/错误/进行中状态和响应式；
8. 算法定义、正确性 oracle、时间/空间复杂度、评分和稳定排序；
9. 保存、缓存、备份、导入导出、隐私和并发；
10. 兼容/全面替换选择、版本、迁移、失败恢复、删除和回滚；
11. 实施顺序、每步生产者与消费者同步；
12. 测试矩阵、真实验收、性能基线、架构/数据/文档门禁；
13. 完成定义、未验证边界和发布授权。

计划中不要把候选方案写成已经确认，也不要把未来测试写成“通过”。若项目有唯一计划目录就更新索引；用户指定外部计划为唯一来源时，不另建仓库内重复计划。

“尚待用户决定”章节只能记录已经在运行中以选择题提出、但尚未回答的事项，并附提问时点；不得把首次发现的问题留到计划交付后才提出。

## 6. 授权门

实施前进行最后一次决策审计：

- 所有会改变语义或迁移的事项都已在发现时通过选择题提出并获得用户答案；
- 计划没有内部冲突或重复 owner；
- 用户已经从“暂不执行”切换为明确实施；
- 目标工作副本和禁止触碰的副本再次确认；
- 外部操作和发布仍按各自授权处理。

若用户说“没有不确定就开始”，只在上述条件均满足时进入实施；否则立即以最小的一批选择题提出剩余问题，不先实施、不等最终报告。
