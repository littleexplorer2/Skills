# 验证、性能与生产交付

## 1. 建立验证矩阵

从风险和合同反推测试，不从现有命令清单反推需求。为每条需求记录：

- owner/合同；
- 最小反例；
- 正常、边界、失败、unknown 和迁移用例；
- 自动测试层级；
- 真实 UI/数据/设备验收；
- 已执行证据、结果和未验证边界。

程序成功结束只证明命令运行，不证明结果正确。验证结论分为：

- verified：对声明的测试范围有直接、可重复的证据；合成最小反例、边界夹具和故障注入也可在各自范围内 verified；
- partially verified：只覆盖部分环境、数据或路径；
- inconclusive：环境、依赖或证据不足；
- not run：明确未执行。

另行记录真实/正式数据、设备、浏览器和生产等价环境的覆盖程度。合成测试通过不能冒充真实环境已验收，真实数据试跑也不能替代边界和故障测试。

## 2. 推荐验证顺序

按项目脚本调整，通常为：

1. 最小反例/领域单元测试；
2. schema、合同、应用用例和 adapter/storage 测试；
3. migration、backup、cache、Worker、取消/恢复和并发测试；
4. feature UI 状态与交互测试；
5. typecheck、lint/format（若项目要求）；
6. architecture/module-boundary/project-reference 门禁；
7. data requirements、data architecture、publication/consumer contract 门禁；
8. build 和本地 preview；
9. 由浏览器子代理执行 render/interaction smoke；
10. 性能 benchmark 与正确性指纹；
11. 完整回归 npm test 或项目等价命令；
12. docs check、branch check、git diff --check 和最终 git status。

先跑定向测试以快速定位，功能闭合后再跑完整回归。最终修复发生在完整回归之后时，至少重跑受影响测试、构建/类型门禁和最终差异检查；高风险改动重跑完整套件。

测试或门禁若暴露新的产品语义、数据处置、兼容范围或验收替代选择，先区分实现缺陷和用户决策。实现缺陷直接修根因；需要用户决定时立即停止相关修复并提出选择题，不跑完整流程后才把选择包装成“测试结论”。

## 3. 正确性优先于性能

性能比较要固定设备、运行时、数据版本、种子、冷/热缓存和重复次数。报告：

- 输出/结果指纹是否相同；
- 准备、首次可行解、完整搜索和证明耗时；
- 访问状态、候选解码、剪枝比例和证明次数；
- 峰值内存、传输/检查点大小、写入和取消延迟；
- p50/p95 或多次分布，而非单次最快值。

剪枝、缓存、并行或传输优化只有在 oracle、pruning on/off 和导入重算一致时才算通过。有限时间内未找到不等于全局无解；中止结果不能冒充全局最优。

## 4. 浏览器与 UI 验证

按 [模型分工](../SKILL.md#模型分工) 将 Computer Use、浏览器调试和 UI 验收交给浏览器子代理。主智能体准备构建与测试环境，依据浏览器证据修复代码。

启动预览前确认：

- server 来自正确工作副本和最新构建；
- 端口没有被旧服务占用，页面标题/版本/资源 hash 与目标一致；
- 使用正式或明确标记的测试数据，不伪造成功状态；
- 结束时停止本轮服务和临时 profile。

至少检查：

- 默认值、设置读写、跨页共享和刷新/备份恢复；
- 主流程从空状态到成功结果；
- 全过滤、未知、待核、冲突、无解、disabled、错误和运行中；
- 动态修改是否及时更新且不产生明显卡顿；
- 关键数值、统计口径和排除项与领域输出一致；
- 窄屏（常用基线可含 390px）、项目定义的 breakpoint 两侧、普通桌面和宽屏；
- 水平溢出、实际元素高度/间距、滚动遮挡、可命中性、内部滚动容器；
- 键盘、焦点、标签、读屏文本、缩放和短屏。

用自动 render/smoke 固化复现过的视觉缺陷，例如记录 viewport、元素高度、间距和 document overflow。截图确认视觉层级，但 DOM/AX/计算样式负责可测不变量。

浏览器自动化出现问题时，浏览器子代理先确认页面、URL、端口、浏览器和 tab，再记录复现步骤及必要的 DOM、控制台或网络证据。遵守当前 Computer Use 技能和工具文档，并在观察到最终可见结果后完成工具要求的收尾。

## 5. 独立审查后的验证

审查意见按以下方式处理：

1. 用代码和最小反例确认，不因模型权威直接接受或否定；
2. 修复根因并加回归；
3. 重跑定向门禁；
4. 若影响共享合同、迁移或算法，重跑完整回归；
5. 把最终增量再次交给代码审查子代理，取得覆盖该增量的审查结论。

Computer Use 发现视觉问题后，主智能体修复代码、重建并重跑受影响的测试，再由浏览器子代理重载页面和复验。

当必需验证受环境限制时，在发现限制时立即让用户从“等待/重试原验收”“接受明确的等价替代证据”“暂停并保留验收待完成”等选项中选择；不要等最终交付才请求接受降级。

## 6. 生产准备

提交、推送、PR、部署、数据发布和正式版同步各自遵循用户的明确授权。按项目发布文档确定目标分支、合并路径和发布检查。正式镜像只按规定的快进或发布流程同步。

### 推送前同步与冲突检查

1. **记录本地状态。** 确认工作副本、当前分支、目标远端和目标分支。用 `git status --short --branch --untracked-files=all`、`git diff` 和 `git diff --cached` 区分本轮工作与用户已有的暂存、未暂存和未跟踪改动。
2. **先获取远端更新。** 用 `git fetch <远端>` 刷新目标分支的跟踪引用，再用 `git rev-list --left-right --count HEAD...<远端跟踪分支>` 判断双方进度。检查远端涉及的文件和改名路径是否与本地改动重叠，特别核对未跟踪或被忽略的同名文件，以及文件与目录同路径的冲突。分叉时，从共同祖先分别检查双方的提交和改动。
3. **安全整合。** 如果只有远端领先、工作树干净且路径检查通过，用 `git merge --ff-only --no-overwrite-ignore <远端跟踪分支>` 同步。如果本地已包含远端提交，可直接准备本轮提交。出现分叉或冲突时，按项目允许的合并或变基流程处理，仅对本轮拥有且未发布的提交做变基。原工作树有用户改动时，保留文件和暂存状态。需要隔离时，在项目允许的独立工作树中从最新远端开始，只移植本轮提交或补丁。根据双方改动逐项解决冲突，涉及用户内容且无法确定如何合并时保留原状并说明具体冲突。
4. **核对提交和待推送范围。** 基于整合后的版本运行项目要求的测试和受影响的检查。清理本轮临时产物，检查受保护数据，运行 `git diff --check` 和 `git diff --cached --check`。仅提交已确认属于本轮的文件或变更块。暂存区有用户的无关改动时，使用隔离工作树，或对完全属于本轮且已被 Git 跟踪的文件使用 `git commit --only -- <本轮路径>`。推送前同时查看 `git log <远端跟踪分支>..HEAD` 和 `git diff --name-status <远端跟踪分支> HEAD`，确认待推送提交和最终差异均在授权范围内，并复查本地其他改动。
5. **推送并核验。** 更新既有远端分支前，用 `git merge-base --is-ancestor <远端跟踪分支> HEAD` 确认远端提交包含在待推送历史中。使用普通推送，例如 `git push <远端> HEAD:refs/heads/<目标分支>`，受保护分支遵循仓库的合并流程。若远端前进导致推送被拒绝，重新获取、检查、整合和验证后再试。推送后用 `git ls-remote <远端> refs/heads/<目标分支>` 核对远端提交，并按发布范围检查 CI、产物、健康检查和回滚点。

未执行生产步骤时明确说“未提交/未推送/未部署”，不要用“已完成”暗示已上线。

## 7. 最终交付

主智能体按 [文本撰写](../SKILL.md#文本撰写) 整理审查发现和验证证据。最终回答先说结果，再给出以下信息。

- 修改所在工作副本、主要功能/架构变化和删除项；
- 关键业务口径，特别是易混淆的计入/排除/unknown；
- 迁移、备份和旧数据处理；
- 实际运行的测试/门禁/benchmark/浏览器证据；
- 独立审查结论及审查后是否又修改；
- 未验证边界、环境限制和已知警告；
- git/commit/push/deploy/服务状态；
- 关键文件的可点击绝对路径。

不要粘贴冗长日志；保留关键数字、退出状态和能支持结论的证据。
最终交付不能首次出现选择题或新未决事项；若仍有阻塞，只能引用运行中已经提出但尚未获得答案的选择。
