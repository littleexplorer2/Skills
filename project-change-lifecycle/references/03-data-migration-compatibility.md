# 数据迁移、兼容与回滚

## 1. 先取得兼容策略决定

当新旧合同无法自然共存时，在写迁移或兼容代码之前立即通过结构化选择题向用户说明并让其选择：

- 全面替换：所有活跃生产者、消费者、调用者、测试和文档原子切换；删除旧活跃路径。适合长期单一口径。
- 有期限兼容：保留单向、最小桥；标明 owner、适用版本、截止条件、删除测试和禁止双写。适合必须读取旧外部格式的情况。

“尽量兼容”不是默认答案。不要为了回滚保留永久双算法；回滚应依靠版本、备份、不可变产物或发布指针。

若调查后仍不清楚旧值如何解释、是否保留旧写入、备份保留多久、失败时自动恢复还是等待确认，分别提供互斥选项和影响，并在对应迁移步骤前取得答案；不得先迁移数据再把选择写进结果报告。

## 2. 迁移设计

每次私人或持久化 schema 变化都应定义：

- 源版本、目标版本和迁移版本号；
- 触发时机、唯一 owner、事务/原子边界；
- 原载荷备份位置、保留期限和恢复入口；
- 成功标志、失败标志、重试/幂等行为；
- 多标签/多进程并发、CAS/revision 和迟到写入隔离；
- unsupported、unknown、partial 和 corrupt 的区别；
- 新代码何时拒绝继续计算，何时允许只读解释；
- 旧缓存、检查点、结果包和导出文件的处理；
- 删除旧写入口和桥的条件。

推荐流程：读取原载荷 → 只读验证 → 建立可恢复备份 → 纯迁移生成候选 → 完整校验 → 原子切换 → 写入版本/receipt → 延后清理。任何一步失败都保留原载荷和诊断。

## 3. 历史数据原则

- 不静默四舍五入、截断、补零、改身份或删除超出新支持范围的原值。
- 新规则不允许的旧值可保留为只读历史/unsupported，但不能继续进入新计算或重新保存成合法值。
- 明确为零、未知和缺失是不同事实；不要把未知当零，也不要把正式零伪造成最小正值。
- 缺少日期、学期、单位、来源或唯一身份时返回 unknown/inconclusive，不挪到当前期、不根据展示文案猜测。
- 多个代码、别名、派生记录和手工记录可能指向同一资源；用正式资源身份去重，不按标题字符串去重。
- 绝对身份用于实际记录、许可、运行和备份；相对身份可保留为培养方案/模板语义。映射由一个领域 owner 负责，展示标签不参与计算。
- 原始/黄金/外部证据保持只读。规范化结果、投影和用户声明必须保留来源与版本。

## 4. 保存、备份与隐私

- 新设置加入现有保存/备份体系，不另建孤立文件或第二个持久化开关。
- 会话、本地持久化、导入导出和备份恢复使用同一 schema 校验和迁移。
- 用户关闭持久化或 privacy epoch 改变后，迟到的异步写入不得恢复已清除数据。
- 不把私人设置、成绩、目标、课程选择或浏览历史加入公开数据请求、日志、遥测、发布包或缓存 URL。
- 导入先预览/校验，失败不污染当前状态；导出明确版本、来源和不包含的内容。
- 配额不足、写入失败、部分导入、重复恢复、跨标签竞争和旧备份都要有测试与用户可见错误。

## 5. 缓存、Worker 与结果版本

- 缓存键包含影响结果的规范化输入、数据 revision、策略版本和算法版本。
- 运行开始时冻结输入；运行中的 UI 编辑只影响下一次运行。
- 应用旧结果前按当前范围、身份、设置和数据 revision 重验，不能只相信旧分数。
- 算法语义改变时升级输入、检查点和结果合同；旧检查点不得续跑新算法。
- 旧结果可只读预览/导出并标明版本；新导入必须用当前唯一 evaluator 重算。
- Worker 消息、存储 DTO 和 UI DTO 同步升级，避免某一层用默认值掩盖版本缺失。

## 6. 删除与回滚

全面替换完成后删除：

- 旧可写入口、字段、默认值、校验分支；
- 重复 evaluator、排序器、容量/筛选算法；
- 失去来源的缓存和转发；
- 已从计划完成的待办文档。

删除前搜索动态导入、脚本、测试、文档、备份恢复和运行时装配。回滚说明应指出如何恢复旧版本和备份；不要在代码里长期双写。

## 7. 迁移验收

至少覆盖：

- 无旧数据、最新版本、每个受支持旧版本；
- 合法、边界、unknown、unsupported、corrupt 和超配额；
- 迁移中断、重复执行、并发、迟到消息和恢复；
- 保存开/关、会话刷新、导入/导出、备份回滚；
- 迁移前后业务不变量及未支持内容不被误报；
- 删除旧路径后没有第二个调用者仍写旧格式。
