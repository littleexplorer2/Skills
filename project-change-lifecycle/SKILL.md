# Project Change Lifecycle

Coordinate a substantial project change from the first requirement through an evidence-backed handoff. Treat planning, implementation, verification, independent review, UI acceptance, and release as distinct states. A plan is never evidence that code works, and passing tests never authorizes a release.

## 目标

在现有项目的真实架构、规则和工作副本边界内完成修改，并留下可追溯的决策、迁移与验证证据。主智能体负责范围、代码、命令、日志和最终结论，并核实子代理提供的证据。

开始时说明正在使用本技能以及原因。仅在用户要求或项目规则允许时改变文件、外部系统、分支、发布状态或生产环境。

## 模型分工

### 角色职责

- 启动流程时，在 Codex 宿主为主智能体选择 `gpt-6.2-sol`，推理强度设为 `max`。主智能体负责执行代码修改和修复、运行本地测试、核对证据并交付。
- 独立代码审查交给 `gpt-6.2-astra` 子代理，`reasoning_effort` 设为 `max`。该子代理负责实质代码、迁移和算法变更的只读初审与修复后的最终增量复核。
- Computer Use、浏览器调试、UI 验收及浏览器复验交给 `gpt-6.1-terra` 子代理，`reasoning_effort` 设为 `max`。该子代理复现问题、执行浏览器检查并提供证据，由主智能体根据证据修复代码。

### 文本撰写

本流程内的所有文本撰写、改写、润色和需要拟人化表达的任务，都使用上文为主智能体设定的模型与推理强度。符合该配置的主智能体直接撰写，需要委派时交给同配置的子代理。范围包括计划、代码注释、技术文档、UI 文案、面向用户的沟通、提交与 PR 说明及交付报告。审查与浏览器子代理提供发现和证据，由负责撰写的智能体据此成稿。

### 子代理派发与复用

1. 需要委派时，先用 `list_agents` 查看本会话的已有子代理，结合创建记录核对模型、推理强度和可用状态。
2. 优先用 `followup_task` 续用已闲置且配置匹配的子代理。复审和复验优先交回已完成前一轮的子代理。每次派发都说明当前工作副本、任务范围和适用规则，并附上最新证据。
3. 已有匹配子代理正在执行且后续工作可顺序完成时，等它空闲后续派。没有匹配的子代理，或匹配的闲置子代理数量不足以覆盖需要同时执行的独立任务时，在宿主并发上限内按缺口新建。使用 `spawn_agent` 时显式指定所需的 `model` 和 `reasoning_effort`，并传入 `fork_turns: "none"`。

若指定配置不可用，报告实际设置或未验证范围，继续可独立完成的工作。必需的审查或验收按选择题门确认替代方案。

## 何时使用

适用于以下任一情况：

- 跨 schema/domain、应用用例、存储、前端或文档的功能修改；
- 会改变数据合同、私人数据、缓存、备份、算法、迁移或兼容策略；
- 需要先写计划、反复澄清产品口径，再实施和验收；
- 面向生产、需要独立代码复核或真实 UI/Computer Use 验收；
- 用户明确要求采用完整项目修改流程。

普通只读问答、单点机械编辑或明确且低风险的小修不必启动完整流程，除非用户明确要求。

## 先选择当前模式

1. 计划模式：用户说“暂不修改”时，只读调查、澄清和写计划；禁止提前实现。
2. 实施模式：只有用户明确授权实施且用户决策已闭合后，才按计划修改。
3. 审计模式：只检查、诊断或复核，不把发现自动修复。
4. 发布模式：提交、推送、部署或生产切换必须另有明确授权；实现授权不自动包含发布。

用户改变模式时立即更新边界。新的需求若补充当前任务则合并；若取代旧任务则停止旧路径，避免继续实现过期方案。

## 运行中的选择题门

把“不清楚”当作运行时阻塞条件，而不是最终报告内容。每完成一次调查、计划、实现、迁移、验证或审查步骤，都检查下一步是否依赖尚未确定的用户意图、产品语义、兼容策略、数据处置、验收替代或发布授权。

- 能由代码、项目规则、正式资料或只读实验查清的技术问题先自行调查，不把技术检索伪装成用户选择。
- 调查后仍存在两个或以上合理方向，且选择会改变可观察结果、数据、长期架构或授权边界时，在执行依赖该决定的动作前立即提问。
- 必须使用当前运行环境允许的结构化选择题界面（例如可用且允许时的 request_user_input）。每题给出 2–3 个互斥选项，推荐项排在最前并说明影响；相关问题可按工具限制小批量提出。
- 如果结构化选择题界面不可用或被更高层规则禁止，不得猜测、静默继续或拖到最终交付；立即停在该决策点，使用宿主允许的即时输入机制，并明确该分支尚未执行。
- 用户未理解时先解释概念和具体例子，再以选择题重新提出；解释本身不算答案。
- 收到答案后立刻更新决策登记、计划、合同和测试，再继续相关分支。已回答事项不得重复询问。
- 最终交付不得第一次披露尚需用户决定的问题；只能复述已经在运行中提出但尚未得到回答的阻塞。

## 核心状态机

按实际风险采用以下状态，不把它们混为一谈：

1. 定界：读取适用规则、项目文档、当前状态和 git status，确认唯一工作副本、分支、禁止写入的镜像及本轮权威计划。
2. 现状调查：找到唯一责任模块、生产者、消费者、调用者、测试、配置、文档和既有迁移；复现或描述当前行为。
3. 决策闭合：区分已确认事实、维护者规则、技术推导、未知项、明确排除和未来事项；发现会改变产品语义或长期架构的事项时，立即通过运行中的选择题门取得决定。
4. 计划：写出 owner、合同、数据流、迁移、删除项、失败恢复、测试、验收、回滚和发布边界。计划仍是未实施状态。
5. 授权门：确认用户已允许实现；若仍要求暂不执行，则停在计划。
6. 实施：主智能体按依赖方向从权威合同和 owner 向消费者执行代码修改，修复根因并删除被替代的重复逻辑。
7. 本地验证：主智能体先跑最小反例和定向测试，再运行与风险匹配的类型、架构、数据、构建、文档、性能和完整回归。浏览器验证按模型分工安排。
8. 独立复核：代码审查子代理只读审查实质代码改动，浏览器子代理调试和验收 UI。主智能体根据复核结果修复问题并重跑相关测试，再交回对应子代理复核最终增量或复验浏览器。
9. 主智能体验收：核对审查意见和实际证据，按已验证范围作出结论。
10. 交付：报告完成内容、未完成边界、验证命令与结果、工作树/发布状态、风险和下一步；不得在此阶段首次提出本应在运行中解决的选择。只有用户明确授权时才提交、推送或部署。

如果后续证据推翻较早结论，应回到相应状态更新计划和决策，而不是在代码中保留两套相互冲突的解释。

## 不可跨越的边界

- 先遵守当前会话、AGENTS.md、子目录规则和项目文档；本技能不覆盖更具体的规则。
- 每条业务规则只能有一个 owner。复用现有实现；接口变化同步所有生产者、消费者、调用者、测试、配置和用户文档。
- 用户说只参考某份计划时，不偷用已被排除的旧计划。多份计划必须先确定唯一来源或明确分工。
- “还有其它必要修改”不授权新增产品政策。由已确认合同必然产生的接线、测试和文档同步可实施；新增用户可见语义、数据删除或长期架构选择必须立即进入选择题门。
- 兼容桥或全面替换由用户决定。桥必须单向、最小、带 owner、期限和删除条件；全面替换要删除旧活跃路径，回滚依赖版本/备份而不是永久双实现。
- 私人数据、原始数据、黄金数据和外部证据默认只读。迁移必须先备份、可恢复、保留无法解释的原值，不静默截断、四舍五入、猜测或删除。
- 不覆盖无关脏工作树，不使用破坏性恢复命令，不把临时测试产物混入交付。
- 程序退出码为零不等于结果正确。缺少依赖、真实数据、GUI 或硬件时明确写未验证。
- 未获授权不提交、不推送、不部署、不发送外部消息，也不把本地预览称为生产发布。
- 发现未决事项时不得先完成一套假设实现再把选择作为“运行结果”交给用户；必须先触发运行中的选择题门。

## 独立复核要求

对完成的实质项目修改，在工具与并发许可允许时：

- 按模型分工派发审查与浏览器任务。要求代码审查子代理按严重度报告可操作缺陷，无发现时明确写 No findings。
- 提供精确的仓库、分支或工作副本，以及适用的 URL、端口和检查重点。明确子代理以只读方式检查项目文件。
- 复核后的实质代码修改须重跑相关测试并交回代码审查子代理复核最终增量。视觉修复后由浏览器子代理复验。

项目规则若禁止子代理或要求其它审查流程，以更具体规则为准。

## 完成判据

只有同时满足以下条件才可说“完成”：

- 已确认需求都有代码或明确排除，且没有悬空用户决策；
- 合同、owner、调用链、迁移、删除项、测试和文档保持一致；
- 用户和项目规定的必需验证已经通过，或用户已基于明确证据调整/豁免该门槛；可选验证的失败或未运行已准确报告；
- 最终代码经过所需独立复核，审查后修改也已复验；
- UI 变更在正确版本和隔离测试状态上完成可见的功能和响应式检查；
- 工作树、临时服务、提交、推送、部署和生产状态被准确报告。

预算不足、时间到、审查尝试失败、环境阻塞或测试未跑完都不是整体“完成”。可以准确报告“实现完成、验收待完成”；用户明确接受等价替代证据或调整完成范围后，才按新范围判断。
